# Aquarium

## Responsibility

`@tankos/aquarium` owns the framework-independent Aquarium aggregate and the
application ports for establishing and reading accessible Aquariums.

## Boundary

The library contains no Angular, Firebase, Firestore, Zod, Material or router
code. Authentication identifies the keeper; authorization decides whether that
keeper has an Aquarium membership and capability. Memberships and permissions
are therefore not embedded in the aggregate contract.

## Current decisions

- An Aquarium is a managed physical system, not a closed freshwater/marine
  type.
- An Aquarium may have multiple keeper members.
- The creator is the initial member/manager; the exact membership and grant
  persistence model remains to be designed with `authz`.
- Creation is private by default and online-required.
- The identity is generated by the application and is independent of the name.
- Routes are owned by `aquarium-ui` and are not fixed here.

## Out of scope

Components, livestock, equipment, measurements, care, public presentation,
offline writes, event sourcing and dashboard composition are separate use cases
or verticals.

## Implementation order

1. Establish the minimal aggregate and domain tests.
2. Define the membership/grant contract with `authz`.
3. Implement the Firestore adapter and Rules tests.
4. Add the UI flow and decide routes from the keeper journey.
