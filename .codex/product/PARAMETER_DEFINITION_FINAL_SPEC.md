# ParameterDefinition — Final Domain Specification

**Status:** final architectural direction for the configurable property
domain.

**Technical audit:** [`PARAMETER_DEFINITION_FIRESTORE_FIWARE_AUDIT.md`](PARAMETER_DEFINITION_FIRESTORE_FIWARE_AUDIT.md)
records the Firestore and FIWARE constraints that implementation must satisfy.
Where implementation safety, service limits or interoperability requirements
conflict with an underspecified detail here, the technically correct solution
prevails and the deviation must be recorded.

**Related plan:** [`PARAMETER_CONFIGURABILITY_PLAN.md`](PARAMETER_CONFIGURABILITY_PLAN.md)

## 1. Purpose and boundary

`ParameterDefinition` is Veril's global catalogue definition for a measurable
quantity. It defines semantic meaning, compatible Units, conversion context,
measurement methods, numeric rules and scientific presentation.

The domain owns catalogue identity, immutable versions, lifecycle,
administrative management and public catalogue reads. Aquarium Management owns
the per-Aquarium selection profile. Measurements own immutable evidence and
embed the definition meaning required to interpret historical readings.

`shared` may expose stable contracts and value objects, but it does not own the
definition repository or CRUD use cases.

## 2. Visibility and authorization

- The catalogue is global and public to all Aquariums.
- An authenticated keeper may create a complete valid definition.
- All users may list and view public definitions.
- A keeper may select an active definition in each Aquarium they manage.
- Only administrators may edit, mark for deletion, restore or physically
  delete definitions.
- Catalogue visibility does not grant catalogue management authority.

## 3. Identity and versioning

The model uses two identifiers:

```text
definitionId   stable logical identity, generated by the server
versionId      immutable identity of one definition version, generated by the server
version        sequential human-readable version number
```

`definitionId` is opaque and immutable. Names, labels and presentation codes
never determine identity or uniqueness. Every edit creates a complete new
version with the same `definitionId`, a new `versionId` and an incremented
`version`.

Versions are immutable. This rule also applies to presentation-only changes;
there are no in-place edits to a persisted version.

## 4. Definition contract

Every version must be complete and valid when created. The minimum semantic
contract is:

```text
ParameterDefinitionVersion
  definitionId
  versionId
  version
  schemaVersion
  lifecycle
  name
  description
  quantityKind
  canonicalUnitId
  acceptedUnitIds
  unitEquivalences
  measurementMethodIds
  methodMetadataRequirements
  numericRules
  displayPrecision
  unitPresentation
  targetEligible
  provenance
```

`name` and `description` describe the property. `quantityKind` describes the
measured magnitude. `canonicalUnitId` is always one of `acceptedUnitIds`.
Accepted and canonical Units use the applicable UN/CEFACT/FIWARE vocabulary;
arbitrary user-created Units are not accepted.

`unitEquivalences` distinguish deterministic conversions from contextual
equivalences. A contextual conversion declares the required metadata, such as
temperature, density, conductivity, scale or measurement method.

`unitPresentation` stores scientifically appropriate symbol, Unicode form,
spacing and placement. Presentation metadata is separate from stable Unit
identity and `unitCode`.

## 5. Provenance and administration

The version records creator and server lifecycle metadata:

```text
provenance
  createdBy
  createdAt
  versionCreatedBy
  versionCreatedAt
  lastAdministrativeAction?
```

Administrative actions record the action, administrator, server time and an
optional reason. Client clocks do not author lifecycle timestamps.

## 6. Aquarium profile selection

An Aquarium profile stores a denormalized selection, not a foreign key:

```text
AquariumParameterSelection
  definitionId
  versionId
  enabled
  selectedAt
  selectedBy
```

The profile does not duplicate or transfer catalogue ownership. Existing
profiles are not migrated automatically when a new version is published.

When a referenced version is marked for deletion, the selection becomes
inactive but remains recoverable. The keeper or an administrator may remove
the inactive selection. It cannot be re-enabled until an administrator
restores the global version. New selections use the active version.

Readers tolerate missing or physically deleted catalogue documents.

## 7. Lifecycle

Deletion follows Veril's general lifecycle:

1. An administrator marks the version/definition for deletion.
2. It becomes invisible to ordinary catalogue and selection flows.
3. It cannot be used for new Measurements.
4. Existing Aquarium selections become inactive.
5. Historical Measurements remain interpretable through their snapshots.
6. An administrator may restore it while it still exists physically.
7. An administrator may later physically delete it manually with confirmation.

No foreign-key cascade or automatic cross-document cleanup is used.

## 8. Measurement snapshot

Every Measurement stores the original definition identity, version and a
self-contained semantic snapshot:

```text
definitionId
versionId
quantityKind
semanticCode
displayName
enteredValue
enteredUnitCode
canonicalValue
canonicalUnitCode
conversionContext?
methodSnapshot?
```

The snapshot is sufficient to interpret the evidence after catalogue editing,
marking for deletion, restoration or physical deletion. Historical evidence is
never rewritten by a catalogue operation.

## 9. FIWARE and Unit interoperability

The model uses the closest applicable FIWARE Smart Data Model, NGSI-LD,
SOSA/SSN and UN/CEFACT semantics. `quantityKind`, `unitCode`, observed value,
observation time, method, source and Feature of Interest remain distinct.

`ParameterDefinition` is a Veril catalogue extension because there is no
directly equivalent Smart Data Model for its global lifecycle. This does not
extend to the evidence model: Measurements and Digital Twin projections reuse
the closest established FIWARE structures from the first implementation slice,
including `WaterQualityObserved` where applicable, NGSI-LD `Property` and
`Relationship`, `unitCode`, `observedAt`, Feature of Interest relationships
and Aquaculture structures such as `FishContainment` or `Sump` where their
semantics fit.

Standard `unitCode` values are used whenever available. Veril does not invent
UN/CEFACT codes. For quantities without a direct standard code or with
method-dependent relationships, the version carries:

```text
standardReference
mappingStatus
measurementMethod
conversionContext
```

This applies especially to salinity representations, dKH, specific gravity
and conductivity. A contextual equivalence is not treated as a simple linear
Unit conversion.

## 10. NoSQL requirements

- Documents contain denormalized identity/version values and snapshots.
- There are no foreign keys or cascade deletes.
- Complete validity is required on create and version creation.
- Deletion, restoration and administrative actions use server timestamps.
- Missing catalogue documents are a supported historical/profile state.
- Rules and trusted server operations enforce authorization independently of
  public reads.

## 11. Acceptance criteria

The domain is ready for implementation when:

- the definition/version/profile/snapshot schemas are explicit;
- Rules distinguish public reads, keeper creation, Aquarium selection and
  administrator lifecycle operations;
- Measurement capture validates the selected version and embeds its snapshot;
- existing fixed-Parameter consumers have a migration path;
- deleted and versioned definitions render safely in history and profiles;
- Unit conversion and FIWARE mapping contracts have executable tests.
